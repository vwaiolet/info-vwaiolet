### 1. 카프카 (Apache Kafka)란 무엇인가?

카프카는 시스템과 시스템 사이에서 데이터를 실시간으로 안전하게 중개해 주는 분산 이벤트 스트리밍 플랫폼임
- 기존의 문제: 서버와 서비스가 많아지면 서로 데이터를 직접 보내느라 연결선이 복잡해지고(스파게티 아키텍처), 한쪽 서버가 죽으면 데이터가 유실되는 문제가 발생했음
- 카프카의 역할: 데이터를 보내는 쪽(Producer)과 받는 쪽(Consumer) 사이에 카프카를 중간 통로로 둠. 보내는 쪽은 카프카에 던져두기만 하면 되고, 받는 쪽은 필요할 때 카프카에서 가져가면 되므로 시스템 간의 의존성이 분리(Decoupling)됩니다.

### 2. 카프카 vs 래빗MQ vs 레디스 비교

세 기술 모두 데이터를 중간에서 중개한다는 점은 비슷하지만, 설계 목적과 장단점이 완전히 다름
| 구분 | 레디스 (Redis Pub/Sub) | 래빗MQ (RabbitMQ) | 카프카 (Kafka) |
| :-- | :-- | :-- | :-- |
| 주요 역할 | 초고속 임시 데이터 송수신 | 정교하고 안전한 메시지 전달 | 대용량 데이터 스트리밍 및 저장 |
| 저장 방식 | 메모리(RAM) 저장 (휘발성 높음) | 메시지 소비 시 즉시 삭제 | 디스크(HDD/SSD)에 영구 보관 가능 |
| 처리 속도 | 가장 빠름 (마이크로초 단위) | 매우 빠름 | 빠름 (대량 처리에 최적화) |
| 라우팅 기능 | 단순함 | 매우 정교함 (원하는 곳으로 정확히 배달) | 단순함 (주제별 분류) |
| 데이터 유실 | 서버 다운 시 데이터 유실 가능성 높음 | 거의 없음 (안정적 배달 보장) | 전혀 없음 (디스크에 기록 됨) |
| 핵심 장점 | 단순함, 극도의 빠른 속도 | 복잡하고 정확한 트랜잭션 처리 가능 | 데이터 재처리(Replay) 가능, 무한 확장 |

### 3. 왜 결국 카프카를 선택할까?

1. 데이터의 영속성 (Persistence & Replay)
    - 일반 브로커(RabbitMQ 등)는 메시지를 수신자가 읽어가면 큐(Queue)에서 지워버림
    - 카프카는 데이터를 디스크에 물리적으로 저장해둠. 덕분에 시스템에 장애가 나서 데이터를 유실했거나, 과거 시점의 데이터를 다시 분석해야 할 때 과거 데이터를 원하는 만큼 다시 재생(Replay)할 수 있음
2. 압도적인 대용량 처리와 확장성 (High Throughput & Scalability)
    - 카프카는 애초에 분산 아키텍처로 설계되었음
    - 데이터 양이 늘어나면 장비를 옆으로 계속 이어 붙이는 수평 확장(Scale-out)이 매우 쉬움
    - 하루 수십억 건의 로그 데이터가 쌓이는 대기업 환경에서도 병목 현상 없이 버텨냄
3. 일대다(1:N) 데이터 배포의 용이성
    - 카프카에 저장된 하나의 데이터 흐름(Stream)을 마케팅 팀, 데이터 분석 팀, 보안 팀 등 여러 부서의 다양한 시스템이 동시에 가져가서 제각각 활용할 수 있음
    - 래빗MQ처럼 가져가면 사라지는 구조가 아니기 때문에 가능함

### 4. 요약

- 레디스는 속도가 가장 중요한 실시간 알림/캐싱에 적합함
- 래빗MQ는 안정적이고 정교한 라우팅이 필요한 비즈니스 메시징에 적합함
- 카프카는 절대 유실되면 안 되는 대용량 빅데이터 파이프라인 및 로그 수집에 가장 적합함
